# NestJS Authentication Core — Prisma + PostgreSQL

This module implements opaque, server-side sessions (not JWT). Browser-to-NestJS requests are direct and use HttpOnly cookies. PostgreSQL is the session source of truth.

## Local setup

Requirements: Node.js 22.12+, npm, Docker Compose.

1. At the repository root, run: docker compose up -d postgres
2. Go to apps/api, copy .env.example to .env.
3. Replace CSRF_SECRET with a strong random secret generated by: openssl rand -hex 32
4. Install dependencies: npm install
5. Generate Prisma Client: npm run prisma:generate
6. Apply schema: npm run db:migrate:deploy
7. Start dev server: npm run start:dev

The API is served at http://localhost:4000/v1.

Local browser origin in .env.example: http://localhost:3000. Browsers have a special Secure-cookie exception for localhost; test real subdomain behavior under HTTPS.

## Endpoints

| Method | Route | Requirements |
| --- | --- | --- |
| GET | /v1/health | Public |
| GET | /v1/auth/csrf | Public |
| POST | /v1/auth/register | Origin + CSRF |
| POST | /v1/auth/login | Origin + CSRF |
| GET | /v1/auth/me | Session |
| GET | /v1/auth/sessions | Session |
| DELETE | /v1/auth/sessions/:id | Session + Origin + CSRF |
| POST | /v1/auth/logout | Session + Origin + CSRF |
| POST | /v1/auth/logout-all | Session + Origin + CSRF |

## CSRF workflow

- Call GET /v1/auth/csrf using credentials: 'include'.
- Send X-CSRF-Token and the exact allowed Origin with every unsafe request.
- The CSRF token expires after 10 minutes and is bound to the current session cookie, if any.
- Fetch a new CSRF token after registering/logging in, because the session cookie changes.

## Security boundaries

- Session cookie is a random 256-bit opaque token; PostgreSQL stores only its SHA-256 hash.
- NestJS checks session, idle/absolute expiry and account activity, and denies private routes by default.
- All unsafe routes require Origin allowlist validation and CSRF protection.
- The session ID changes on successful login/register. Logout revokes server state.
- Production cookies require Secure, HttpOnly and a compatible SameSite setting.
- Default API-host-only cookie does NOT reach Next.js SSR on a different subdomain.
- Multi-instance rate limiting requires an additional shared throttling store.

The code includes Vitest unit tests, PostgreSQL-backed E2E tests and CI configuration. CI results must be reviewed before treating the implementation as ready for deployment. This phase does not include the Next.js app, OIDC, MFA, password reset, or resource-level authorization.
